# LocalSpace 逻辑问题分析

> 生成时间：2026-08-01  
> 范围：Go 后端（`app/`）、Wails 绑定层、Vue 3 前端（`frontend/src/`）  
> 共 10 项主要问题 + 4 项补充提示

---

## 1. 单文件导入：数据库写入失败后源文件丢失（严重）

- **文件**: `app/services/file_service.go:193-231`
- **问题**: 代码先通过 `os.Rename` 将源文件移动到目标目录，再写入数据库记录。如果 `fileRepo.Create` 失败，虽然会删除目标路径 `destPath`，但源文件在 `Rename` 时已经被移走，无法恢复。
- **复现场景**: 用户导入一个文件，刚好触发数据库唯一约束、磁盘已满或 JSON 序列化失败，文件会从磁盘永久消失。
- **建议（修订版）**:
  - 改为**分阶段提交**：先复制到临时文件 → 写数据库记录 → 原子重命名 → 删除源文件。
  - 临时文件统一放在**目标 master 目录下的 `.localspace-temp/` 子目录**中，例如：
    ```
    <master-dir>/.localspace-temp/<filename>.localspace-importing
    ```
  - 临时目录与最终目录同盘，保证 `os.Rename` 原子；失败时用户也能在对应存储目录下找到残留。
  - 各阶段失败清理策略：
    | 阶段 | 失败情况 | 清理动作 |
    |---|---|---|
    | 复制到 temp | 中断/磁盘满 | 删除 `tempPath` |
    | checksum / 重复检测 | 计算失败 / 是重复文件 | 删除 `tempPath` |
    | 创建 DB 记录 | 数据库写入失败 | 删除 `tempPath` |
    | 重命名 temp -> final | 被占用/权限 | 删除 `tempPath`，删除刚创建的 DB 记录 |
    | 删除源文件 | 权限/被占用 | 导入已成功；记录日志，不阻塞 |
  - 启动时增加 `CleanupOrphanedTempFiles()`：扫描所有 master 目录下 `.localspace-temp/`，删除创建时间超过阈值（如 24 小时）的残留临时文件。

## 2. 单文件导入跨盘符时只复制、不删除源文件

- **文件**: `app/services/file_service.go:193-197`
- **问题**: 当源路径与目标路径不在同一卷时，`os.Rename` 失败，代码回退到 `copyFile`。复制成功后从未删除源文件。
- **复现场景**: 用户将 D 盘文件导入到 E 盘存储目录，导入后 D 盘原文件仍保留，与同盘导入的“移动”行为不一致。
- **建议**: 与问题 1 一并用分阶段导入修复：统一先复制到目标 master 目录的 `.localspace-temp/`，数据库记录创建成功后再重命名到 final，最后删除源文件。这样无论是否跨盘，行为都是一致的“移动”。

## 3. 文件列表存在 SQL 注入风险

- **文件**: `app/repositories/file_repository.go:147-157`
- **问题**: `sortBy` 和 `sortOrder` 从 `FileFilter` 直接拼接到 SQL 的 `ORDER BY %s %s`。
- **复现场景**: 任何能控制 `FileFilter.SortBy` 的调用方（包括未来前端新增排序功能）传入 `id; DROP TABLE files;--` 即可执行任意 SQL。
- **建议**: 对 `sortBy` 做白名单校验（如仅允许 `id`、`created_at`、`modified_at`、`file_name`），`sortOrder` 仅允许 `ASC`/`DESC`。

## 4. DeleteFile 先删物理文件再删数据库记录

- **文件**: `app/services/file_service.go:725-746`
- **问题**: 先 `os.Remove(file.FilePath)`，再更新 storage size，最后才 `fileRepo.Delete(id)`。
- **复现场景**: 数据库删除失败（约束冲突、只读等）时，文件已消失但记录仍保留，前端显示一个打不开的“幽灵文件”。
- **建议**: 先删除数据库记录，再删除物理文件；或把两步放进事务/临时状态机中。

## 5. RenameFile 回滚失败会导致数据库与文件路径不一致

- **文件**: `app/services/file_service.go:773-786`
- **问题**: 物理重命名成功后，若数据库 `Update` 失败，会尝试 `os.Rename(newPath, originalPath)` 回滚。若回滚也失败（权限、目标被占用），文件实际在 `newPath`，但数据库仍存 `originalPath`。
- **复现场景**: 重命名时目标目录被其他程序占用或权限变化，回滚失败。
- **建议**: 在数据库更新成功后，或者先记录预期新路径再重命名；必要时把重命名也纳入重试/事务。

## 6. Job 执行 goroutine 没有 panic 恢复

- **文件**: `app/services/job_service.go:334-437`
- **问题**: `runJob` 内部没有 `recover()`。如果 handler（如批量导入）触发 panic，goroutine 直接退出，不会把 job 状态更新为 failed。
- **复现场景**: 批量导入过程中遇到未处理空指针或越界，整个 goroutine 崩溃，任务在数据库里永远卡在 `running`/`recovering`。
- **建议**: 在 `runJob` 顶部加 `defer recover()`，panic 后记录错误并把 job 状态设为 failed。

## 7. 关闭应用时数据库可能在后台任务仍在写入时被关闭

- **文件**: `app/services/job_service.go:283-320` + `app/app.go:74-82`
- **问题**: `PrepareForShutdown` 只调用 `cancel()` 取消上下文，不等待 goroutine 真正结束。随后 `App.Shutdown` 直接 `a.db.Close()`。
- **复现场景**: 用户关闭窗口时批量导入正在写入 `batch_import_items` 进度，数据库先关闭导致写失败甚至 panic。
- **建议**: `PrepareForShutdown` 使用 `sync.WaitGroup` 或通道等待所有 `runJob` goroutine 退出后再返回；`Shutdown` 在 close DB 前确认没有运行中的任务。

## 8. OpenFileLocation 使用字符串拼接构造 PowerShell 命令

- **文件**: `app/app.go:420-423`
- **问题**: `powershell -Command explorer.exe '/select,"%s"'` 直接把文件路径拼进命令字符串。
- **复现场景**: 虽然 Windows 路径通常不含特殊字符，但仍存在命令注入或引号解析失败风险；且依赖 PowerShell 中间层。
- **建议**: 改用 `exec.Command("explorer", "/select,", absPath)`，Windows 原生支持并避免字符串拼接。

---

## 9. 前端 API 包装器把所有后端错误静默吞掉

- **文件**: `frontend/src/api/index.ts:96-119`
- **问题**: `safeWailsCall` 在 Wails 调用抛错时 `resolve(fallbackValue)`，而不是 reject。例如 `api.file.list` 出错返回 `[]`，`api.theme.getConfig` 出错返回默认对象。
- **复现场景**: 数据库损坏、路径不可写、AI 调用失败等真实错误无法传递到 UI，用户只能看到空数据或默认值，无法定位问题。
- **建议**: 区分“Wails 不可用”（浏览器开发环境）与“Wails 调用失败”。后者应 reject，让调用方决定如何展示错误。

## 10. 批量导入临时路径设计不合理且清理函数对 finalPath 的删除条件过于宽松

- **文件**: `app/services/file_service.go:470-484`
- **问题**: 当前批量导入临时路径直接放在最终目录且使用 `destPath + ".localspace-importing"` 作为后缀；`CleanupBatchImportArtifacts` 还会删除 `finalPath`，只要它的路径以 `.localspace-importing` 结尾。
- **复现场景**: 正常逻辑下不会命中，但这是一个危险启发式：如果用户合集名或文件名恰好以该后缀结尾，真实文件可能被误删；且临时文件散落在最终目录中，不易管理。
- **建议**: 批量导入也统一使用目标 master 目录下的 `.localspace-temp/` 子目录（如 `<master-dir>/.localspace-temp/<job-id>/<item-index>/filename.localspace-importing`），按任务 ID 集中管理；清理时只删除明确已知的临时路径，不再把 finalPath 作为候选删除目标。

# 补充提示（非 TOP 10，但建议关注）

## A. 缩略图缓存未校验文件内容变更

- **文件**: `app/services/file_service.go:957-962`
- **问题**: `thumbnailIsCurrent` 只按文件名（缓存 key）判断，未校验文件内容是否变更。
- **后果**: 文件内容被外部修改但 ID/类型不变时，可能仍显示旧缩略图。
- **建议**: 结合文件修改时间或校验和判断缓存是否过期。

## B. 前端文件列表每次都全量加载

- **文件**: `frontend/src/store/modules/files.ts:68`
- **问题**: `loadFiles` 始终向后台传 `fileType='all'`，前端再做类型过滤。
- **后果**: 文件量大时性能差，且分页逻辑未真正利用。
- **建议**: 将 `fileType` 传给后端做过滤，或实现分页懒加载。

## C. 单文件导入时元数据提取类型不准确

- **文件**: `frontend/src/views/ImportView.vue:346`
- **问题**: 单文件模式调用 `api.system.getMetadata(path, 'file')`，传了不准确的 `fileType='file'`。
- **后果**: `ExtractMetadata` 中图片/视频分支无法进入，只能拿到文件大小，图片宽高、视频时长等元数据丢失。
- **建议**: 根据文件扩展名解析真实类型后再调用 `getMetadata`。

## D. 并发导入时临时文件名可能冲突

- **文件**: `app/services/file_service.go`（未来修改区域）
- **问题**: 如果多个导入任务同时处理同名文件，临时路径 `<master-dir>/.localspace-temp/<filename>.localspace-importing` 可能互相覆盖。
- **后果**: 并发导入同名文件时，临时文件互相覆盖，可能导致 checksum 错误、重复检测失败或数据混乱。
- **建议**: 临时文件名加入唯一标识，如 `<filename>-<timestamp>-<random>.localspace-importing`；或按任务/会话划分子目录。
